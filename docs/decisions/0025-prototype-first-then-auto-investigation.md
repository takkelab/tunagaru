# 0025 試作品を先に縦に一本通し、自動調査はその次に足す

- 状態: 採用
- 日付: 2026-11-15

## 背景

これまでの実装の順番では、評価と比較（10人分の正解リストが必要）がステップ4にあり、画面はステップ8だった。体験の芯（[ADR 0022](0022-overlaps-of-seed-people-as-core.md)）を確かめる前に、インフラと評価が先に来ていた。

本人は「好き」を記録しないので、アプリが自分で記事を集めなければ、重なりは増えない。つまり、Web検索で記事を探す自動調査は、おまけではなく中心の機能になる。また本人の経験では、インタビュー記事は「人名 インタビュー」より「作品名 インタビュー」で見つけやすく、検索結果には歌詞やリリース情報のサイトが多く混ざる。

費用の見込み（2026年11月時点。実装時に再確認すること）: Claude の Web 検索は1,000回あたり$10で、トークン代は別にかかる。Haiku 5.5 は入力$0.10／出力$0.50（100万トークンあたり。プロンプトが10万トークンを超えると5倍）。1人を5回の検索で調べると、検索料だけで約7.5円になり、抽出のトークン代は1円未満になる。起点が10〜20人なら、最初にまとめて調べても約200円になる。

## 決定

- **受け入れテストを、最初の試作品の目標にする**: 2人分の根拠（記事のURLと、動画の文字起こし）を入れると、吉本ばななが重なりとして出て、タイムスタンプつきの根拠から元の場面に飛べる。
- 実装の順番を、次のように変える（[process](../spec/process.md#実装の順番と完了条件)）。
  1. 外部アダプタ → 抽出器 → DBと名寄せ → 調査パイプライン → API → 画面（ここまでで試作品になる）
  2. **自動調査**: Web検索は、記事のURLを見つけるところまでに使う。本文の取得、事前フィルタ、抽出、キャッシュは、試作品の経路をそのまま使う。検索語は「作品名 インタビュー」「人名 好きな本」「人名 好きな曲」などの型を、起点の作品一覧から組み立てる。歌詞やリリース情報のサイトは、検索の対象から外す。
  3. 評価と比較（[ADR 0006](0006-source-and-model-selection-by-evaluation.md)）
  4. 統合、グループとメンバー、MusicBrainz、Wikipedia、Wikidata P737 の取り込み、Batch
- **Web検索は、「深掘り」に限らず調査の標準の経路にしてよい**（[ADR 0007](0007-monthly-budget-500-yen.md) の費用削減策6を変更する）。代わりに、調査1回あたりの検索回数に上限を設け、最初の数人で1人あたりの実費を測ってから、上限の値を決める。月500円のハード上限は変えない。
- 試作品では、予算の仕組みを簡単にする。ジョブは1つずつ順に実行し、開始前に「当月の実費＋見積もり≦上限」を確かめる。並行ジョブの予約と精算は、ジョブを並行で動かすときに入れる。

## 検討した代替案

- 今の順番のまま、評価を先にする: 体験が良いかどうかを、画面がない状態では確かめられない。正解リストを作る手間も先にかかる。
- 自動調査を最初の試作品に入れる: 本人の使い方には合うが、URLを貼る経路が動く前に検索を足すと、うまくいかないときに原因を切り分けにくい。自動調査の経路は試作品の経路を再利用するので、後から足しても作業が無駄にならない。
- Web検索に、記事の本文の取得と抽出までさせる: 本文がキャッシュされず、事前フィルタも効かないので、費用が予測しにくい。

## 結果とトレードオフ

- 抽出の品質を数値で比べるのは、試作品のあとになる。それまでは、受け入れテストの2人と本人の目で判断する。
- ステップの番号が変わる。古いADRに書かれたステップ番号とリンクは、この順番に合わせて直した。
